# Heartbeat management and ingress

Heartbeat configuration belongs to a service and environment. Only an administrator can create, edit, disable or issue/revoke a heartbeat grant. Creation defaults to disabled; enabling starts an absolute deadline from the transaction's database clock. Editing uses an expected configuration version and invalidates the old deadline in the same transaction. Disabling never asserts recovery for an existing missed heartbeat.

Grants authorize only `heartbeat:write` for one heartbeat. The response to issuance contains a random bearer token once. Storage and authentication use its SHA-256 hash; audit events contain only configuration versions and grant IDs. Expiry must be in the future and no more than 90 days from issuance. Create a replacement grant before revoking the previous grant. Revocation and pings serialize on the heartbeat/source lock.

The machine endpoint accepts only a JSON object containing `version: 1`, a unique `eventId`, and UTC `observedAt`. An exact retry returns its original receipt and does not extend the deadline. A different event with an older or equal observation is rejected. The trusted routing scope comes from the bearer grant, never from the body or browser session. A successful ping after a persisted miss emits explicit recovery through normal alert processing and its recovery hold.

The shared HTTP adapter caps raw input at 2,048 bytes, rejects malformed UTF-8 and unknown fields, and emits static errors without storage details. Both hosts enforce the same limit while streaming, reject compression, and cap body-read time at ten seconds. The dedicated deadline lane runs alongside paging and probe lanes without replacing them.

HTTP results: 202 for a new receipt, 200 for an exact retry, 400 for invalid input, 401 for invalid/expired/revoked grants or unauthorized scope, 409 for a stale observation, 413 for excessive body size, 415 for unsupported media type, and 503 when storage or host activation is unavailable. Standalone mounts `POST /v1/heartbeats/:probeId`; Dashboard mounts `POST /api/v1/escalator/heartbeats/:probeId` (respecting its configured API prefix). Application administration stays on tRPC in both hosts. Dashboard derives actors from enrolled WorkOS organizations, rejects enabled configuration writes while the separate paging broker is unavailable, and returns 503 on machine ingress while that binding is absent. Disabling and revoking remain available to authorized administrators.

Unit tests cover version conflicts, permissions, token redaction, revocation, disabled-state preservation, payload limits, retry receipts, rollout denial and redacted failures. PostgreSQL execution remains opt-in with the test database procedure from the persistence part; no live database or external heartbeat client was run.
