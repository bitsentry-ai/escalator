# Metrics query support

D6 supports Prometheus `GET /api/v1/query_range`, directly or through Grafana's Prometheus datasource proxy at `/api/datasources/proxy/uid/:uid/api/v1/query_range`. This is separate from Grafana alert intake. Other datasource query formats and native histogram results are unsupported.

Protocol references checked on 2026-10-03: [Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/) and [Grafana datasource proxy API](https://grafana.com/docs/grafana/latest/developer-resources/api-reference/http-api/api-legacy/data_source/). The supported response is a matrix of timestamp/string-value pairs. Both APIs are exercised through synthetic recorded-response fixtures shaped from those documented protocols, not production captures. No live Prometheus or Grafana instance was contacted for validation.

Configure two read-only expressions returning exactly one aggregate series each: total requests and failed requests for the same service/environment and the same non-overlapping interval. The values must be interval counts, not rates, percentages or cumulative counters. For a 60-second interval, a representative expression is `sum(increase(http_requests_total[60s]))`; the error expression must select a subset of that same traffic. Administrators must verify their instrumentation and query semantics. Floating-point counts are supported because counter extrapolation can produce fractional values. The adapter cannot prove that two arbitrary expressions describe the same traffic.

The errors expression must return a zero-valued series when nothing failed. Prometheus returns an empty result, not zero, when the error-labelled series does not exist, for example after a restart or for a service that has never failed. The adapter never zero-fills, so an empty errors result is recorded as missing data: the monitor stays insufficient and can never emit a clear or recovery signal, and an open metrics incident stays open. End the errors expression with `or vector(0)`, for example `sum(increase(http_requests_total{code=~"5.."}[60s])) or vector(0)`. Use this fallback only on the errors expression, and only when it selects a subset of the same counter as the requests expression, so a scrape outage still leaves the requests result empty and therefore missing. Never add it to the requests expression.

Range endpoints are inclusive and aligned to whole-second steps from 60 to 3,600 seconds. A request spans at most one day. The upstream query timeout is four seconds, each HTTP exchange is bounded to five seconds and 256 KiB, and the pair has a ten-second cancellation deadline. A two-series return limit detects accidental non-aggregated queries; any response containing more than one series is rejected. Production hosts must provide the existing destination-policy transport, with DNS pinning, redirect revalidation and private-network approvals. The adapter never performs unrestricted fetches itself.

Authentication uses an opaque secret ID and a persisted job claim. The secret is a JSON object with one `authorization` header value, used only over HTTPS. Basic and bearer authorization can be provisioned in that header; plaintext, endpoint URLs and expressions are excluded from observations and errors. Returned provenance contains provider, datasource UID, query hashes, label-set hashes and the exact requested range. Persistence later adds the source/configuration version and database receipt time.

Gaps are explicit null values. Non-finite values, negative counts, errors exceeding requests, unsafe counts and provider annotations are marked unusable. No zero filling, implicit series aggregation or healthy fallback occurs. A provider error or rejected response returns a static error. A successful query alone is not a health verdict, and an upstream query's apparent completeness cannot prove scrape freshness.

## Sustained-floor predicate

The version-1 evaluator requires a complete ordered grid covering the configured window, enough samples, nonzero traffic in every interval and a minimum total request count. It compares the lowest interval error rate with the configured floor: every interval at or above the floor yields active; at least one below the floor yields clear. Source recovery holds still apply after a clear signal. Missing, annotated, non-finite or inconsistent values yield insufficient data, never clear.

This pure predicate deliberately evaluates historical windows as well as current ones. The live job must enforce freshness and configuration/lease fencing; replay must filter by database receipt time before calling it. Those persistence and runtime integrations are the remaining T3.8 work. No missing denominator is inferred from error webhooks.
